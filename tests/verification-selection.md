# Выбор проверок: содержательные случаи

Сверять с common `references/verification.md`, portable implement/review и
run/publish/install/update. Это проверка контракта инструкций, не модельный
пилот и не доказательство скорости/надёжности тестов. Команды задаёт потребитель.
Во всех случаях коротко назвать change → consumers → risks → checks/results/gaps.

| Изменение / условия | Ожидаемый выбор и границы |
| --- | --- |
| Только документация, исполняемые контракты не изменены, политика разрешает узкий набор | Проектный gate, ссылки/структура и содержательная сверка. Если это инструкции/шаблон, проверить потребителей и получаемый текст. Не добавлять UI/full regression ритуально; не утверждать, что UI проверен. |
| Модель состояния/общий контракт | Тесты инвариантов, ошибок, границ плюс реальные потребители модели и зависимые интеграционные сценарии. Не ограничиваться unit одного файла. Gate перед интеграцией; полный набор по риску/политике. |
| UI и взаимодействие | Затронутые состояния/сценарии, потребители событий/модели, необходимые визуальные/браузерные проверки в проектной матрице плюс gate. Не удалять браузеры/сценарии ради скорости. Незатронутый полный набор — не автоматическое требование. |
| Build config / зависимости | Проверки сборки, зависимых runtime/пакетных контрактов, выдаваемого артефакта по риску и gate. Маленький lock/config diff не означает малое влияние; расширить до полного набора при требовании политики/недоказанной границе. |
| Неизвестная область влияния; политика требует full при неизвестном риске | Полный regression обязателен; недоступный runner/красный шаг блокирует соответствующую приёмку, не заменяется зелёным узким набором. |
| Политики нет/она неоднозначна, прежний hook запускает полный набор | Не сокращать hook/gate; установить согласованную политику с владельцем. До этого сохранять требования. MIS install/update не переписывает AGENTS/CI автоматически. |
| Потребитель явно требует full на каждый push | Выполнить полный набор, даже для docs/package maintenance. Общая оптимизация MIS не отменяет это правило. |
| Тот же снимок прошёл implement checks, review и публикация исходников | Передать evidence с identity/условиями; не повторять только из-за этапа. Действующие hooks/CI выполняются: иное окружение может защищать иной риск. Не требовать полной приёмки только потому, что будет push. |
| Merge/правка/hook изменили tree, либо зависимости/окружение изменились при том же tree | Переоценить потребителей/риски, выполнить инвалидированные проверки, подтвердить gate и reassessment нового целого снимка. Для неизменённых частей явно обосновать применимость старых результатов; не переносить общий pass автоматически. |
| Публикация проверенной сборки A, затем пересобрали B | Evidence A не доказывает B; выдать A с точным source/artifact ID либо проверить B/доказать идентичность по правилам проекта. Git push сам по себе не является выпуском. |
| Быстрый gate зелёный, full не запускался/красный/содержит непроверенные skips; один flaky rerun зелёный | Только gate pass; полная приёмка не подтверждена. Один повтор не доказывает исправление нестабильности. Не ослаблять assertions и не менять продукт ради pass; перенос теста на другой уровень объясняет сохранение риска. |

Контекст Snyrk иллюстрирует разные уровни, а не норматив времени: сокращение
обычного gate не считается ускорением сохранённого полного regression.
