# Проверочные случаи гранулярности планирования

Это ручные содержательные сценарии для `mis-port-op-plan-tasks` и `mis-flow-plan`,
не автоматический тест поведения модели. Сравнивать границы и покрытие, а не число
Task или дословные названия. Каждый proposal должен иметь эффект, «как увидеть»,
критерии, исключения, основание посильности и только реальные зависимости.

## 1. Игра: таблица, бой, меню, поражение

Синтетические достаточные требования: локальная одиночная игра без сохранений;
из меню начинается новая партия; в таблице можно бросить пять кубиков, удержать
выбранные, перебросить до двух раз, записать сумму в свободную строку; затем ход
переходит в бой, записанная сумма наносит урон одному врагу, живой враг отвечает
фиксированным уроном; победа возвращает к таблице со следующим врагом, нулевое
здоровье игрока показывает поражение, откуда можно начать чистую новую партию.
Существующая основа: приложение запускается, есть кнопки, тестовый runner;
вся игровая механика новая. Здоровье игрока 20, каждого врага 30, ответный урон 3;
здоровье ограничено снизу нулём, при победе ответа нет, баланс вне scope.

**Неприемлемо:** четыре Task «меню», «весь режим таблицы», «весь бой»,
«интеграция и полировка MVP» без оценки нагрузки. Вертикальность двух режимов
сама по себе не доказывает посильность; слои «модель → UI → тесты» тоже не решение.

**Приемлемое направление** (не обязательный шаблон/квота):

- Из меню начать партию, бросить кубики один раз и увидеть их значения в таблице.
- Удержать часть кубиков и перебросить остальные с проверяемым лимитом.
- Записать сумму в свободную строку; занятая строка отвергается без потери хода.
- Запись запускает бой с одним врагом и наносит вычисленный урон, видимый в UI.
- Живой враг отвечает уроном, после обмена возвращается управление таблице.
- Победа начинает следующий цикл с новым врагом, сохраняя положенное состояние.
- Поражение и повторный старт дают новую чистую партию без состояния прежней.

Каждый шаг проверяет только своё добавление на уже рабочей основе и регрессии;
ещё не добавленные правила явно исключены. Начальные срезы не объявляются MVP.
Сверить все требования с Task и совместный цикл от меню до рестарта. Число Task
может отличаться при доказанно иной сложности/готовой реализации. Большая одна
веха допустима; перенос всех задач в одну Task — нет.

## 2. Маленькая известная работа

Есть целочисленная функция и тестовый runner; требуется удваивать точный `int`,
отвергать остальные типы, включая `bool`, без побочных эффектов.
**Ожидание:** одна Task с примерами, rejection-проверками и основанием посильности.
Не отдельные Task на функцию, тест, документацию, review или публикацию.

## 3. Мало кода, много неизвестного

Запрос «подключить облачные сохранения» не определяет провайдера, авторизацию,
конфликты и offline-поведение. **Ожидание:** назвать существенные пробелы,
получить продуктовые решения и исследовать существующие контракты ограниченно.
Не обещать одну маленькую executable Task из-за предполагаемого малого diff,
не изобретать требования и не создавать research/design Task автоматически.

## 4. Перепланирование и неполное покрытие

В игре случай 1 базовый бросок уже закрыт с доказанным результатом; удержание
начато, бой пока крупная открытая Task. **Ожидание:** сохранить ID/историю и
начатые обязательства, предложить bounded delta для оставшегося перегруза,
не повторять готовое, не удалять/закрывать старую запись молча. Победа, поражение
и рестарт не исчезают из покрытия. Зависимости означают необходимые результаты,
а не просто порядок перечисления или общие файлы.
