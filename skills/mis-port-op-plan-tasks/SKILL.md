# Посильная работа с проверяемым результатом

Вход: выбранный результат/веха, существенные требования и решения, ограничения,
критерии, источники, наблюдаемая реализация, существующие работы всех статусов и
известный граф, применимые правила проверок. Достаточны прямые требования;
отдельные spec/design, AC IDs, предварительный технический план не обязательны.
Caller получает недостающие решения и отвечает за запись. Метод не зависит от
трекера, Git, структуры проекта или других скиллов.

1. Ищи **минимальный набор посильных Task**, а не минимальное число записей.
   Одна Task достаточна только если весь её цикл посилен одному агенту в одном
   рабочем контексте с запасом на проверки и исправления после review.
   До выбора границ проверь объём контекста: необходимые источники/подсистемы,
   новые контракты и решения, сценарии/состояния и матрицу проверок. Несколько
   самостоятельных механик, смена нескольких режимов, пересмотр нескольких
   контрактов или необходимость держать большую часть проекта одновременно —
   признаки чрезмерного scope. При таком признаке сузь срез либо обоснуй по
   фактам, почему он всё ещё посилен; неизвестный объём не считай малым.
   Не рассчитывай на compaction, более мощную модель или делегирование как
   замену декомпозиции. Не назначай квоты задач, токенов, строк, файлов или часов:
   размер diff сам по себе не измеряет нагрузку и риск скрытой ошибки.
   Разделяй по самостоятельным проверяемым результатам, реальной зависимости,
   необходимой параллельности или нагрузке на исполнителя. Объясни split.
   Установка, код, тесты, review, документация и публикация одного результата —
   внутренние действия, не отдельная цепочка задач.
2. Для каждой единицы укажи полезный результат, контекст/границы и исключения,
   конкретные проверки (включая ошибки, числа и запреты), применимые источники и
   решения. Техническая задача не требует продуктового предлога. Если задан Bug,
   сохрани наблюдаемое/ожидаемое поведение и воспроизведение, не придумывай его.
   Продуктовая Task по умолчанию — минимальный вертикальный срез: сквозной
   сценарий через необходимые слои с наблюдаемым пользовательским эффектом.
   Разделение по слоям само по себе не основание для split; исключение обоснуй
   реальной предпосылкой/ограничением. Для каждой Task опиши ожидаемое изменение
   и как его увидеть: условия, точка входа/команда, действия, ожидаемый эффект.
   Для технической работы достаточно наблюдаемого технического результата.
   Не выдумывай неизвестный адрес/команду: предварительный сценарий caller
   уточнит по реализации, без обязательного отдельного документа.
   Большой вертикальный срез дели на более узкие сквозные сценарии: базовый путь,
   затем отдельное правило, ветвь, тип взаимодействия или переход состояния.
   Каждый шаг должен давать заметный проверяемый прирост на рабочей основе,
   не требовать незавершённых будущих Task для собственной приёмки и сохранять
   ранее работающие сценарии. Непокрытое поведение явно исключи из его scope
   и сопоставь другой работе, а не теряй из критериев вехи. Не дроби до отдельного
   обработчика/файла/теста без самостоятельного эффекта. Включи короткое основание
   посильности: что меняется, какие контракты уже известны и что остаётся снаружи.
3. Сопоставь с открытыми, начатыми и закрытыми работами по смыслу, источникам и
   фактическим эффектам; сохрани ID, историю и чужие обязательства. Верни отдельно
   unchanged, добавления и ограниченные правки. Неизвестный эффект create требует
   reconciliation, а не нового имени. Не удаляй и не закрывай старые записи.
4. Добавь только необходимые зависимости «blocked → prerequisite», с причиной и
   точными существующими ID либо явно локальными обозначениями новых единиц.
   Учитывай внешние пути, циклы, соседние вехи. Membership не задаёт порядок;
   общие файлы/приоритет не доказывают blocks. Незавершённая определённая
   предпосылка допускает планирование с блокирующей связью, но не исполнение.
   Неизвестный обязательный контракт оставь пробелом, не изобретай дизайн.
5. Сверь каждое требование/критерий с предлагаемой или доказанной существующей
   работой. Назови проверку совместного результата, если отдельных проверок мало;
   она не требует отдельной Task. Убери дубли, необоснованные splits/edges,
   скрытые исключения и неподтверждённое покрытие.
   Повтори проверку посильности после покрытия: не спрятаны ли внутри одной Task
   несколько самостоятельных результатов или вся интеграция MVP в последней
   «склеить всё» Task. Проверяй интеграцию по мере добавления срезов. Небольшая
   известная работа остаётся одной Task; число экранов или название MVP сами
   по себе не задают ни число вех, ни число Task.

Верни минимальные единицы с полями, optional Epic membership, покрытие,
направленные зависимости и причины, точный delta к известному состоянию,
пробелы/существенные вопросы и первую потенциально доступную работу. Полнота
декомпозиции не означает готовность к исполнению. Не выдумывай ID, не сохраняй
план, не назначай исполнителей и не начинай следующую стадию.
