# Фиксированный контракт проекта

Планирование/исполнение MIS работают в подготовленном проекте со следующими средствами.
Явный `/mis-install` может подготовить пакет и Beads в существующем Git-проекте;
он не создаёт приложение и не выбирает его продукт/стек/тестовую стратегию.

| Компонент | Соглашение |
| --- | --- |
| Harness | OpenCode **2.0.27+** с доступными нативными worktree/session инструментами; проверить реальную сборку |
| Tracker | Beads CLI `bd`, готовое workspace проекта, native `epic`, `task`, `bug`, `blocks`, операции чтения/записи/публикации |
| VCS | Git, один репозиторий = один MIS-проект, известная основная ветка и публикационный remote |
| Knowledge | `docs/product/`, `docs/spec/`, `docs/rules/`, Markdown/OKF |
| Agent instructions | Корневой `AGENTS.md` указывает на проектные требования и правила |
| Agent profiles | Доступные для делегирования `standard` и `advanced`; конкретные модели/варианты и разрешения задаёт пользователь в нативной конфигурации OpenCode |
| Skills | Локально установленные скиллы **MIS** и команды `mis-plan`, `mis-bug`, `mis-run`, `mis-status`, `mis-install`, `mis-update` |

**MIS не имеет `mis.yaml`.** Нет выбора worktree adapter, tasks adapter, OKF-пути или модели lifecycle. Нет автоматического поиска альтернативного трекера или создания приложения. Настройки Beads остаются нативными: `.beads/`, embedded Dolt, remote того же Git-репозитория и `refs/dolt/data`; живая БД не коммитится в primary branch. Существующий иной workspace установщик не мигрирует без отдельного решения.

## Шаблоны GitHub

Новые приложения могут создаваться из GitHub Template под соответствующий стек. Шаблон содержит продуктовую структуру и проектные правила/проверки, но **не гарантирует** уникальную инициализацию Beads. `/mis-install` проверяет реальное состояние и подготавливает/восстанавливает workspace явно; существующая удалённая история имеет приоритет перед fresh init.

Если Git, `bd`, связанный remote или необходимые каталоги отсутствуют, `mis-plan`/`mis-run` сообщают конкретную причину и не выполняют скрытый init, миграцию или установку пакетов.

## Где определена специфика приложения

В `docs/rules/` самого потребителя: команды build/test/lint, TDD либо standard, пирамида тестирования, UI/визуальные проверки, правила CI, архитектура, локализация, инфраструктура и обращения с внешними ресурсами. MIS не задаёт эти решения глобально. В `docs/product/` — что строим; в `docs/spec/` — что уже конкретно реализовано.

## Совместимость и ограничения

Не внедрять поддержку иного harness, monorepo со многими MIS-проектами, произвольных адаптеров трекера или «план Б» для отсутствующего native worktree. Поддержку расширять только по отдельному требованию.
