# Общие эксплуатационные правила MIS

## Без формальных пауз

Полное поручение `/mis-plan` или `/mis-run` разрешает обычные действия в своей области: исследования, ограниченные изменения, тесты, ревью, публикацию и закрытие Task. Отдельные подтверждения для каждого подшага не требуются. **Не приравнивать это к разрешению** менять чужую работу, удалять данные, форсировать Git/Beads или нарушать средовые ограничения. Обращаться к человеку только при содержательной развилке, запрещённом действии или недостающей полномочности.

## Beads

Использовать только CLI/API `bd`, не писать напрямую во внутреннее хранилище. Перед mutating-операцией проверить точный ID, тип, статус, assignment и directed `blocks`; после — перечитать результат. Уникальность названия задачи не гарантирует уникальность сущности: сверять кандидатов по смыслу и существующим состояниям. Beads/Dolt имеет отдельную историю и отдельную публикацию, не путать с Git.

## Worktree и сессия

Перед изменением Git-проекта — проверенный linked worktree для конкретной Task (кроме подтверждённого non-Git случая). При повторном запуске сначала найти старую рабочую копию; не перезаписывать чужие/грязные файлы. Не допускать параллельных независимых writers в одной копии. Переход `session_move` проверять отдельным последующим действием. Не использовать `force` при удалении/переходах; не удалять грязную рабочую копию. Нативное управление OpenCode может быть недоступно в фактической версии — тогда зависимую часть остановить и диагностировать, а не тихо переключиться на Worktrunk.

## Изоляция исполнения

Git-worktree не изолирует процессы, порты, БД, кэши и выходные файлы. Применять
общий контракт `mis-proj-lib-common`: владение собственными экземплярами,
динамическое выделение адреса при bind, передача фактического адреса всем клиентам,
проверка нужной копии и освобождение только своих ресурсов. Предварительный probe
не резервирует порт; при необходимости фиксированного адреса конфликт допускает
ограниченный повтор по правилам проекта. Изменяемые данные и артефакты разделять
по копии/запуску либо сериализовать конфликтующие операции. Не требовать конкретного
языка, фреймворка или нового MIS-реестра; не обходить реальные ограничения среды.

## Review

Ревью фактического целевого снимка выполняет отдельный контекст, отличный от автора/исправителя. Уточнить применимость в зависимости от вида изменений; для изменённого исполняемого поведения independent review — нормальный обязательный gate. После критичных правок обновить относящиеся к ним проверки и ревью. Не требовать отдельного YAML-отчёта на каждый review, если результат пригоден в самой сессии и может быть достоверно передан публикации.

## Git publication

Публиковать точный проверенный снимок своей рабочей копии в установленную главную удалённую ветку без force и без включения посторонних коммитов. Учесть upstream, возможные конфликты и валидность тестов/ревью после интеграции; подтвердить удалённую ревизию. Не считать локальный commit публикацией. Не выполнять скрытый deploy: deployment/release управляет pipeline и правила проекта.

## Resume

При повторном вызове по ID восстановить факты: текущий Beads, привязанный worktree и Git состояние, документацию и опубликованный результат. Выполнить только отсутствующую часть. Не создавать обязательный handoff.md, журнал переходов или отдельный реестр task→worktree. Если фактическая связь копии с Task не может быть установлена — не угадывать по одному названию ветки.

## Отчёт

Коротко указать реальные изменения и проверки, отдельные доказательства Git и Beads публикации, блокировки и рекомендуемое следующее действие. Не выдавать частичный результат за `ok`.
