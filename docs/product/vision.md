# MIS — видение

## Цель

MIS (Minimal Implementation Skills) — самостоятельный пакет Agent Skills для OpenCode 2.0, использующий Beads как единственный трекер задач и Git для версионируемых изменений. Он помогает по высокоуровневым требованиям сформировать достижимые вехи и задачи, а затем автономно реализовать их через проверку и публикацию.

Гипотеза: современный агент способен самостоятельно определять нужную глубину технического планирования и реализации. Пользователь описывает желаемый результат, а не проходит обязательные этапы Feature Specification → Design → Technical Plan.

## Обязательные принципы

- **Два основных workflow**: `/mis-plan` и `/mis-run`; `/mis-bug` собирает и исследует один запрос изменения в Beads, `/mis-status` читает состояние, `/mis-install` явно готовит установку/Beads, `/mis-update` обновляет только пакет. Другие атомарные скиллы подгружаются при необходимости.
- **Никакого MIS-конфига**: поддерживается один заранее определённый стек инструментов и одна структура проекта.
- **Никаких Beads Formulas** в первой версии. Добавить позднее только при доказанной пользе.
- **Веха может быть продуктовой или технической**: «работает окружение» так же легитимно, как «есть играбельный MVP».
- **Единица планирования — проверяемый результат**, не список технических микрошагов.
- **Разделение намерения и реализации**: `docs/product/` — верхний уровень, Beads — согласованные результаты интервью и работы, `docs/spec/` — проверенная детализация реализованного поведения.
- **Проектные правила имеют приоритет** в выборе технологий, архитектуры, тестирования, TDD и CI/CD.
- **Агент завершает порученную операцию**, а не просит формального согласования каждой стадии. Существенное продуктовое противоречие или реальный запрет требуют уточнения; неопределённые технические детали решаются самостоятельно.
- **Надёжность не отменяется простотой**: изоляция изменений, проверки, независимое ревью, проверяемая публикация, возобновление после сбоя.

## Общение с пользователем

Все проектные операции MIS, включая установку и обновление, ведут один диалог
на языке пользователя: простой язык, без внутреннего жаргона и необщепринятых
сокращений; необходимые специальные термины объясняются при первом употреблении.
Вопрос или сообщение о проблеме содержит достаточно контекста: что происходит,
почему это важно, последствия и какое решение либо действие требуется от человека.

Задавать строго один вопрос за раз и ждать ответа, без нумерации вопросов.
При содержательном выборе давать нумерованные варианты, первым — ровно один
обоснованно рекомендуемый, оставлять возможность своего ответа. Для открытого
или фактического вопроса не выдумывать меню или рекомендацию. Лёгкие маркеры:
**❓ Вопрос**, **💡 Рекомендую**, **✅ Подтверждено** — последнее только для
действительно принятого ответа. Не повторять отвеченное и не создавать
формальных пауз при достаточных данных. Правила действуют и без интервью;
подробности — [общие правила диалога](../../skills/mis-proj-lib-common/references/dialogue.md).

## Вне границ первой версии

- Произвольные трекеры, разные платформы для агентов, плагины адаптеров и универсальная конфигурация.
- Технические стадии как записи Beads, обязательные SDD-файлы, Feature-иерархия между Epic и Task.
- Formulas / Molecules / Wisps, планирование спринтов, отдельная команда Next/Status.
- Создание приложения/стека и скрытый bootstrap: plan/run/update диагностируют неготовность, но не инициализируют Beads. Только явный `/mis-install` подготавливает отсутствующий embedded workspace либо восстанавливает удалённую историю.
- Отдельные Research и Delivery типы задач. Исследование при нужде — обычная Task; сборка/релизные pipeline задаются проектом.
- Worktrunk и собственные Git-worktree-адаптеры. Используется нативный runtime OpenCode.
- Технологии приложения: никакого Phaser/Rails/TDD по умолчанию на уровне MIS.

## Критерий успеха

В подготовленном демонстрационном проекте агент без дополнительной истории диалога умеет: (1) сформировать Epic и Task из `docs/product/`; (2) выполнить Task в собственной рабочей копии; (3) актуализировать spec, если создано новое устойчивое поведение; (4) провести проверку/ревью; (5) подтвердить Git и Beads-публикацию; (6) вывести следующую осмысленную рекомендацию. См. [критерии MVP](../build/acceptance.md).
