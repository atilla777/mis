# Модель работ

## Сущности

| Понятие MIS | Представление Beads | Семантика |
| --- | --- | --- |
| **Milestone** | Нативный `epic` | Достигнутое проверяемое состояние проекта, продуктовое либо техническое. |
| **Task** | Нативный `task` | Ограниченная конкретная работа с проверяемым результатом. Может иметь Epic или быть самостоятельной. |
| **Bug** | Нативный `bug` | Дефект: наблюдаемое поведение, ожидаемое поведение, воспроизведение и исправление. По ситуации связывается с Epic. |
| **Dependency** | Нативная связь `blocks` | Реальное блокирование одной работы результатом другой. |
| **Membership** | Нативная родительская связь | Принадлежность Task к Epic; сама по себе не означает порядок исполнения. |

Не создавать Feature, Phase, Story, Subtask как обязательные уровни. Не делать отдельные типы Product/Technical/Research/Delivery; технические и продуктовые Task исполняются единым `mis-run`.

## Что записывать

**Epic**: осмысленная цель/значимое состояние, критерии готовности, существенные границы и ссылки на требования. Состав Task может уточняться без переписывания цели. Milestone не сводится к «все дети закрыты»: критерии проверяются по результату.

**Task**: ясный результат, значимый контекст и ограничения, критерии проверки, ссылки на применимые `docs/product/` и существующие `docs/spec/`. Не требовать технический план, предварительный дизайн, отдельную спецификацию или дочерние задачи. Если нужная конкретика получена в интервью, сохранить её в этой записи.

**Bug**: фактический сбой, ожидаемое поведение и доступный воспроизводимый случай. Не считать текущее поведение кода нормативным, если оно конфликтует с `docs/product/` или `docs/spec/`.

**Связи**: только native Beads API/CLI. Не дублировать списки зависимостей в текстовых полях; при желании пояснять смысл, но источником графа остаётся трекер. Не создавать блокирующие связи только для удобства последовательного списка.

## Пример технической вехи

Epic «Проект готов к разработке»: успешный локальный запуск, рабочие тесты и CI. Task «Создать скелет приложения», «Настроить проверки» и другие — только если действительно независимы и достаточны. Для одной небольшой технической работы достаточно отдельной Task без Epic.

## Завершение

Task закрывается после подтверждённого изменения, применимых проверок и необходимых публикаций. Epic проверяет собственные критерии на фактическом состоянии проекта после закрытия обязательных задач. Недостающая работа оформляется новой/обновлённой Task; Epic остаётся открытым. Административное закрытие без выполнения критериев не выдавать за достижение вехи.
